Application processes

Network applications communicate as process pairs

Process means a running program. In networking, we describe communication as one process exchanging messages with another process on a different host.

Socket Interface

A socket connects an application process to the transport layer

A socket is not an application-layer protocol. It is the programming interface that a process (in the application layer) uses to request transport services for sending and receiving application data.

Application protocol answers: “What format and meaning does this message have?”
Socket answers: “How does the program send and receive messages through the operating system?”

DNS

DNS looks up information associated with a domain name

DNS is an application-layer protocol. The application asks a resolver process for a DNS record. The resolver creates a query and uses the socket interface to send the query and receive the DNS response through the transport service.

DNS structure and data

DNS hierarchy and resource records

DNS hierarchy Organizes names from broad to specific: root → TLD → delegated domain or zone → host/subdomain labels.
Resource records Typed entries such as A, AAAA, MX, and NS that store information associated with a DNS name.
Why we need them They distribute name management and help applications locate the correct host or service efficiently.

HTTP state behavior

HTTP requests are independent; applications add continuity

Stateless protocolEach HTTP request contains the information needed to process that request. The protocol does not automatically remember the previous one.
Application stateLogin, cart, preferences, and workflow progress are maintained by the application, not by HTTP alone.
Separate conceptA persistent connection may carry many requests, but connection reuse does not make HTTP stateful.

Stateless protocol

Each HTTP request is independently understandable. A TCP connection or cookie does not change that core message model.

Stateful application

Login, shopping carts, and preferences require continuity. The application creates that continuity above HTTP.

Cookie safety

HTTP evolution

HTTP evolved mainly to deliver many web objects more efficiently

HTTP/0.9minimal

GET only; no headers or status line; one simple HTML response.

→
HTTP/1.0metadata

Headers, status codes, content types, and additional methods. Connections commonly closed after a response.

→
HTTP/1.1reuse

Persistent connections by default, required Host header, chunked transfer, and stronger caching support.

→
HTTP/2multiplexing

Binary framing, compressed headers, and multiple streams over one TCP connection.

→
HTTP/3QUIC

HTTP over QUIC/UDP with integrated TLS 1.3, independent streams, and faster recovery from loss.

1.0 → 1.1Reuse a TCP connection instead of repeatedly opening one.
1.1 → 2Multiplex streams and compress headers while retaining HTTP semantics.
2 → 3Move from TCP to QUIC to reduce transport-level blocking and improve mobility/recovery.
Unchanged: methods, status codes, headers, and request–response meaning. Improved: framing, concurrency, connection setup, and loss recovery.

DHCP across subnets

Why a DHCP relay agent is needed

A new client sends a local broadcast, but routers normally do not forward broadcasts. A DHCP relay agent forwards the request to a DHCP server on another subnet.

💻
DHCP Client Sends DHCPDISCOVER on its local subnet.
Local broadcast
↪
DHCP Relay Agent Receives the broadcast and forwards it as a routable message.
Forwarded request
🖥
Remote DHCP Server Selects the correct address pool and returns the reply through the relay.

Why students should know this

In real networks, one central DHCP server often supports many subnets. Without a relay, the client’s initial broadcast would remain only on the local subnet.

Relationship with DNS

DHCP can provide the address of a DNS resolver. After configuration, the client sends DNS queries to that resolver. DHCP configures the host; DNS resolves names.

Email services

Email flow: simple and correct

1

Sender MUA

The sender writes the email in a mail app.

Message includes headers, body, and attachments.
2

SMTP submission

The mail app sends the message to the sender mail server.

Commonly SMTP submission on port 587.
3

DNS MX lookup

The sender server asks DNS which mail server handles the receiver domain.

DNS helps find the destination server; it does not carry the email body.
4

Receiver mail server

The sender server relays the email to the receiver server, which stores it in the mailbox.

Server-to-server delivery commonly uses SMTP.
5

Receiver MUA

The receiver reads or syncs the mailbox using IMAP or POP3.

IMAP syncs with the server; POP3 usually downloads mail.
